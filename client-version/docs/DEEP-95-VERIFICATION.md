# Deep correctness, access and performance audit - release 95

This audit covers the maintained client product and current screenshot-sale workflow. Production operational records, accounts and edited plans are preserved. Test mutations use fresh synthetic records in an internally networked PostgreSQL QA service with SMTP disabled. Other VPS applications and the earlier full edition are independent.

## Confirmed fixes

1. **Call updates could use an old sale state.** Recording an outcome now takes the same nonblocking sale lock used by correction, review and SR reconciliation, refreshing cached state before validation. A concurrent cancellation/product correction cannot leave a call recorded against stale eligibility. Technical postponement uses the same lock. PostgreSQL tests prove a busy sale returns 409, a cancelled sale stays cancelled and an independent sale still proceeds.
2. **Specific grants could outlive general workspace access.** General workspace roles now need their basic read grant as well as a specific mutation/export grant. Support updates and report exports cannot bypass removed read access. Calling roles deliberately keep their dedicated stage grants instead of broad workspace read access; removing a stage's read grant blocks its queue and recording actions. Role ceilings and sign-out ownership checks remain intact.
3. **Assigned-stock details crossed team-leader boundaries.** Team leaders see their own agents' assigned assets and the shared branch pool. Another leader's assigned items and movements are excluded from the register, history and exports. Branch aggregate balances remain available without exposing another team's personal stock detail.
4. **Stock export filters ran after the row cap.** Branch, category, status, agent and dates now apply in SQL before the existing 1,000-row bounds for stock, requests and SIM/asset movements. Valid older records in a selected branch are no longer hidden by newer unrelated records. Offset timestamps normalize to UTC; inverted ranges are rejected. Existing caps remain bounded rather than becoming unbounded downloads.
5. **Stock pages repeatedly reloaded related records.** Branch, sales-agent and user relationships are retained in the request's identity map in batches. The 50-item regression previously needed 154 queries and now permits at most 14. Asset-history authorization checks the selected row instead of materializing every authorized asset ID. Movement queries join/filter related stock before limiting results.
6. **Opening one call history fetched every sale history.** The web panel requests the selected sale only and keys its cache by sale and authorized branch. Actor references are batched. The optional API filter preserves legacy callers and intersects existing agent/branch access.
7. **Busy colleagues could exhaust an office IP's API limit.** Verified, unexpired bearer tokens now use a bounded per-member API bucket. Unauthenticated traffic, sign-in and session limits remain IP based; work-location collection keeps its tighter member limit. Forged/expired tokens cannot create trusted member buckets, and bearer-scheme casing cannot bypass the cap. Authorization/session revocation still runs on every protected endpoint.

8. **Outdated Python dependencies had published advisory matches.** FastAPI, Starlette and PyJWT now use compatible patched releases; the image build also updates pip. The candidate runs FastAPI 0.146.0, Starlette 1.9.0 and PyJWT 2.15.1. Access and refresh tokens issued by the prior QA image still authenticate and rotate after replacement. Current versions and compatibility requirements were checked against [FastAPI on PyPI](https://pypi.org/project/fastapi/0.146.0/), [Starlette on PyPI](https://pypi.org/project/starlette/1.9.0/) and the [official PyJWT release](https://github.com/jpadilla/pyjwt/releases/tag/2.15.1). The scan does not imply every advisory path was reachable in this application.

9. **The dependency update changed how routers are included.** The full regression run caught an excluded field-task endpoint becoming reachable because nested routers are now lazy. The edition filter now applies recursively before the first request. The final candidate exposes 170 included API routes, excludes field tasks from routing and OpenAPI, and the authentication-dependency audit traverses included routes. A separate nested-router regression checks that allowed routes remain usable. The incompatible candidate was never deployed.

## Test-harness corrections

The initial full backend run passed 775 cases and exposed an old migration test referring to a removed `captures.func` alias. It now imports SQLAlchemy's function helper directly; migration/data behavior was not changed. The candidate runtime intentionally excludes the PDF-reader test helper; QA installs the already-declared `requirements-dev.txt` helper separately. Initial access assertions were corrected to preserve the intentional dedicated-call-grant model rather than accidentally granting calling staff broad workspace read rights.

A notification test assumed a fresh account always had a Transactions item. It now verifies an empty category and opens an available authorized item when present, escaping literal labels safely. Overlapping browser runs initially shared Playwright's artifact directory, causing missing trace files; final runs use separate output directories and run connected mutation groups sequentially. The initial shared-IP 429s also led to the confirmed member-bucket fix above. No sign-in safeguard was weakened to make tests pass. The repeated mobile call test now types through the actual Flutter input and waits for one filtered action, avoiding a race between semantic-input acknowledgement and framework rendering.

## Release and limits

Five API source files, Python dependency/build pins, the focused web history change, the ICCID display label and compiled web assets are published. The schema remains 023; no database migration or data reset is required. The normal Android APK and mobile-demo bundle stay on build 94 and consume the same corrected API. A read-only physical check on the unlocked Android device opened Home, branch SIM stock, Assets & supplies, requests, notifications, profile and Support after deployment. Those screens loaded and were visually inspected; the existing sales-agent session was returned to Home off shift, with no sale, ticket, draft or location session created. The candidate image is built from the current production image with those five source changes and the pinned dependency updates; runtime source hashes and health are checked against the isolated QA database.

Deployment/database backups, isolated restore and table fingerprints, environment/mobile hash preservation, the previous API image and a rollback path are required before publication. Client policy inputs still on hold are unchanged. Carrier activation, payment settlement, real email Inbox delivery, every possible image/device condition and production-scale capacity are not claimed as verified by this audit. Geofencing rejects missing, stale, uncertain and mock-marked positions but relies on device-reported measurements; it is not cryptographic device attestation. Request limits remain per API process. A future multi-process rollout needs shared/distributed admission controls rather than assuming the current single-process buckets are global.
